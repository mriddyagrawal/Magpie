## 1. What changed today, in one paragraph

We did two parallel pieces of work that meet in the middle:

1. **Bundle diet** — shrank the production install footprint by ~3 GB by
   re-routing the deep-learning runtime through a CPU-only package index,
   carving optional dependency groups so the default contributor install
   stays small, and deferring a heavy import that was inflating cold start.
2. **Distribution pipeline** — locked an end-to-end plan for shipping
   signed installers on macOS / Windows / Linux, wrote the cross-platform
   Python-sidecar build script, wired the desktop shell's auto-updater
   end-to-end (frontend module, Tauri Rust plugin, app config, CI), and
   migrated the release workflow onto the upstream Tauri release action.

The branch is **not yet shippable** — code signing certificates, the
update-feed manifest, and Tier 2 (--onefile) / Tier 3 (full installers)
verification are still open. But every load-bearing component for those
final steps is now in place and individually testable.

## 2. Components changed or created

Each entry describes a single artifact by what it *does*. The current
filename is intentionally omitted; the renaming proposal is in the chat
companion to this document.

### A. Slim-distribution components

**A1. Python project manifest with installer-aware dependency groups.**
Declares three opt-in groups — *contributor / packager / notebook user* —
so the default install stays minimal. Pins the deep-learning runtime
explicitly and routes it through a CPU-only package index, which removes
~13 vendored CUDA wheels from the resolution. CUDA users opt back in via
an environment variable at install time.

**A2. Frozen, deterministic dependency graph.**
The lockfile counterpart to A1. Net change: −1690 lines, zero `nvidia-*`
entries (was 13+). This is the file CI installs from.

**A3. Lazy-import patch in the content-routing layer.**
Moves a heavy validation library import from module top to first use.
Cold-start time for the affected import path dropped from 2.06 s to
0.83 s (≈60% reduction).

**A4. Diagnostic audit script for unused model architectures.**
Lists every Hugging Face transformer architecture currently importable
from our locked deps that we do *not* use at runtime — input to the
PyInstaller `--exclude-module` list (deferred, see §3).

**A5. Bundle-diet plan document.**
Written record of the diet decisions: per-PR rationale (A → F), expected
size deltas, what's deferred and why.

### B. Distribution-pipeline components

**B1. Packaging brainstorm document.**
Exploratory doc — three-tier delivery model (`uv` install → onefile
binary → native installers), asset-storage plan for ML weights, signing
strategy, update channels. Superseded by B2 once approved.

**B2. Locked packaging implementation plan.**
The shippable plan: P10-1 through P10-7 (project hygiene, sidecar
build, packaging glue, code signing, release workflow, auto-updater,
release process). Includes acceptance criteria per phase and a
"verify on a working-disk box" checklist.

**B3. Cross-platform Python sidecar build script.**
Wraps PyInstaller with the right `--collect-all`, `--collect-submodules`
and exclude flags for our actual runtime (Hugging Face transformers
backbones, `colpali_engine`, `fastembed`, `sentence-transformers`).
Produces a single executable per OS that the desktop shell spawns.

**B4. Frontend auto-updater module.**
Single async function: checks the update feed once on launch, downloads
and installs in the background, relaunches. All failures are silent
warnings — updates never block the user. Exposes a non-silent variant
for a future "Check now" UI.

**B5. Frontend boot integration.**
The two-line addition to the app entry point that calls B4 at startup.

**B6. Tauri runtime updater plugin registration.**
The Rust-side wiring: declares the updater plugin in the crate's
manifest and registers it in the application builder.

**B7. Tauri app config — updater section.**
JSON declaration of the update endpoint URL pattern, the embedded
public key for signature verification, and `dialog: false` so the
updater UX is fully driven by B4 (no native modals).

**B8. CI release pipeline.**
GitHub Actions workflow that runs on every push, every PR, and on
manual dispatch. Cross-platform matrix (macOS / Windows / Linux),
builds the Python sidecar via B3, then hands off to the upstream
Tauri release action which produces signed .dmg / .msi / .exe /
.AppImage artifacts and (on tags) cuts a draft GitHub Release with
the update-feed manifest auto-populated.

**B9. Local build/dev recipes.**
The task-runner file. Recipes for syncing each dep group, building
the sidecar in stub mode for `tauri dev`, building the sidecar for
real, printing the dependency-group cheat sheet, and running the
full local pipeline.

## 3. What is deliberately NOT done yet

- **Tier 2 verification**: the onefile sidecar binary builds, but a
  real cold-start latency / disk-footprint comparison vs. the dev
  environment hasn't been recorded.
- **Tier 3 verification**: native installer artifacts (.dmg / .msi /
  .exe / .AppImage) have not been built end-to-end on a working-disk
  machine — the local filesystem here had I/O errors that prevented a
  clean re-sync.
- **PyInstaller exclude list (PR-E from the bundle-diet plan)**: A4
  produces the candidate list, but the excludes have not yet been
  applied to B3.
- **Code signing**: certificates, keychain wiring, and notarization
  steps are scoped in B2 §P10-4 but not yet implemented in B8.
- **Update feed hosting**: B7's endpoint URL points at a placeholder.
  Real hosting (S3 / CloudFront / GitHub Releases) is pending.
